## 2026-09-02 — Sprint E7: triage-first panel, personal criteria, all-strategy scoring

- **Unknowns split from settings.** Triage now shows only the ONE (or two) UNKNOWNS a strategy needs — BTL: rent; Flip: end value (+ refurb inline); BRRRR: end value + rent + refurb; HMO: room rent (+ rooms) — and a "Using your settings ⚙" link to a separate in-panel **Settings** screen holding every other input (deposit, rates, fees, voids, bridging, LTV, opCosts, licence, tax basis, ICR stress, …). Nothing is removed from the maths, only from the triage screen. The £1.5m Gower Road listing dropped from ~18 visible fields to 1 (BTL) / 2 (Flip, HMO) / 3 (BRRRR). Unknowns stay per-sector for rent and per-listing for the rest; settings + criteria are global.
- **Personal criteria (the point of the sprint), in core.** `listing/criteria.ts` lets the user set their own bars — minimum cashflow / ROI / ICR, minimum profit (Flip), plus deposit % and rate — which `thresholdsFor()` substitutes into the strategy thresholds where set, and `customKeysFor()` flags so the headline names THEIR number ("… under the £2,000 cashflow you set as your minimum."). Every field is optional and defaults to today's config value, so behaviour is unchanged until touched. Stored locally. Lives in core so the web app can adopt it later; the web app's own scoring is unchanged (scoreDeal gained an optional `opts.customKeys` — backward-compatible). **Judgment call:** the brief's Flip "minimum margin" has no corresponding gate in the config's Flip score (its gates are profit + ROI), and adding one would change the web's Flip verdict (forbidden this sprint), so Flip criteria = minimum profit; a distinct margin gate is deferred. Also, the single min-ROI applies only where a strategy has an ROI gate (BTL/HMO), not to Flip's different-scale return.
- **All four strategies score in-panel — no "needs analyser" dead ends.** `scoreListing` now builds Flip/BRRRR/HMO inputs exactly as the web's verdict islands do and calls `scoreDeal`. Where a component genuinely can't be judged from a sale listing — HMO room-size legality (no room dimensions) — `roomSizeFailures` is passed as `null`, the room-size component scores **'unknown'** ("check in the analyser"), the HMO can't be Green on unverified rooms, and the rest of the verdict still computes. (`HmoInputs.roomSizeFailures` is now `number | null`; the number path is unchanged for the web.)
- **Smart defaults — labelled suggestions, never facts.** HMO lettable rooms suggested `= bedrooms`; Flip/BRRRR end value suggested from our R2 sector data (typical £/m² × floor area, else typical price), with NO suggestion + a stated reason when the sector has too few sales. Rent has no honest free source, so it is never invented — left to the user but remembered per sector.
- **Bug 5a fixed — floor-area RANGE.** Rightmove can publish a range ("4,216-4,910 sq ft / 392-456 sq m"). `rightmoveFloorArea` now parses both ends, uses the **midpoint** as the working value (a stated convention) and exposes the range; the panel shows "392–456 m² (a range on the listing; using the 424 m² midpoint)" instead of silently taking 456. A `NormalisedListing.floorAreaSqmRange` field carries it; a hand-authored synthetic fixture (`fixtures/listings/synthetic/rightmove-floor-area-range.html`) + tests cover it.
- **Bug 5b fixed — outside the evidence.** When the subject price is above the sector p90 by more than `thresholds.evidenceOutsideFactor` (default 2), price-vs-sold returns **'outside-evidence'**, the panel says "No nearby sales at this level — we can't judge the price from sold evidence," and the price component is EXCLUDED from scoring (unknown) rather than scored as a fail. Verified on the £1.5m Gower Road listing against a £469k-ceiling sector.
- **Layout** (triage): property line → strategy switch → score + headline → what's holding it back → components → the one/two unknowns → "Using your settings ⚙" → Send to my analyser. Brand + a11y as before (lime CTA on near-black text). Send-to-analyser round-trips ALL the new fields.

(4) HMO 7+ rooms are now refused as a large sui-generis HMO (mirroring the web) instead of scored as a small HMO. (5) A pre-filled smart-default suggestion couldn't be blanked (redraw re-injected it) — a per-field 'cleared' flag now lets the user empty it, and the chip notes when a score rests on a suggested value. (6) a11y: the property line is an `<h1>` and the Settings headings `<h2>`. (7) Added tests for the BRRRR-LTV gate, the HMO sui-generis gate, the Flip mis-attribution, and the minIcr/minProfit/ratePct criteria paths.

## 2026-09-02 — Sprint E5: versioned portal extractors + R2 remote config

- **Extractors live in @gil-bricks/core (`src/listing/`), the extension is a thin adapter.** `extractListing(portal, document, config, url)` reads the page the user opened — Rightmove `window.__PAGE_MODEL` (flatted) and Zoopla `self.__next_f` flight + `ld+json` — from the DOM's `<script>` tag TEXT in the ISOLATED world, and returns a normalised listing where every field is `{value, status}` with status `found | missing | unavailable-on-this-portal` (never a silent null). Each extractor is versioned (`rm-1.0.0`, `zpl-1.0.0`) and the version is recorded on every result.
- **Hard rule held — no main-world injection needed.** The serialised data is present in the script tags' text content, which a content script reads directly from the shared DOM; we never touch the page's `window.__PAGE_MODEL`/`self.__next_f` globals (main world) and never inject. So the "unavoidable main-world injection" escape hatch was NOT used.
- **Config-driven, redesign-survivable.** Field paths / flight keys / fallback meta selectors / flags / thresholds live in a remote JSON (DATA only); all parsing LOGIC stays in the package (MV3 rule). Operator can retarget a reader after a portal redesign by editing one file — no code change, no store re-review. **R2 key `config/extractors.json`**, URL `https://pub-ed7263f454104eb1a02055393ee15800.r2.dev/config/extractors.json`. An identical `FALLBACK_CONFIG` ships in the extension (`src/listing/extractors.config.json` is the byte-for-byte upload artifact; a test asserts it equals `FALLBACK_CONFIG`).
- **Where the remote fetch happens (judgment call).** host_permissions stay EXACTLY the two portals (E4 rule). The remote config is fetched from the side panel (an extension page) via CORS from our public R2 bucket — no host permission needed, and it falls back to the shipped copy on any failure (timeout/blocked/offline), never blocking first paint. The content script makes **no network request at all** — it reads the cached config (chrome.storage, the "storage" permission) or the shipped fallback, then reads the DOM. So `r2.dev` was NOT added to host_permissions.
- **Feature detection + honest failure.** Primary embedded blob → DOM fallback (OpenGraph/meta; Zoopla also `ld+json`) → typed failure (`no-blob | shape-changed | not-a-listing | unreadable`) with a plain-English message. A fallback that can only find an id/url (nothing substantive) is treated as a failure, not a hollow success.
- **Postcode → sector + E&W gate (pure, no network).** `postcodeToSector` derives the sector id from the postcode string (e.g. `SA1 8AJ → SA1 8`) and rejects Scotland/NI/Crown-dependency areas with the SAME message the web app uses (`Sorry — this covers England & Wales only`). Judgment call: I duplicated the small OUTSIDE_EW area set into `listing/postcode.ts` rather than refactor the web-tested `comparables/geocode.ts` — lower risk; the two are noted as mirrors.
- **Capability table (what's reliably available — this decides what we can show):** floor area is NOT in Rightmove's model (reliable on Zoopla); Rightmove has no structured auction flag (reliable on Zoopla); Zoopla exposes no "reduced/added" update reason without price history (reliable on Rightmove); first-live date is Rightmove-only when "Added" (always on Zoopla via publishedOn); Zoopla floor-plan comes as image filenames, Rightmove as full URLs. All other core fields (id, price, type, tenure, beds, baths, postcode, address, newBuild, description) are reliable on both.
- **Tests.** Golden normalised object per fixture (committed `fixtures/listings/golden/*.json`); a corrupted embedded blob triggers the DOM fallback (`source: 'dom'`); a fully-stripped page triggers an honest typed failure; the remote-config fallback works with the fetch failing / wrong-shaped / from a persisted cache; postcode/E&W gate; the whole run is guarded so it makes ZERO network calls. `happy-dom` (dev-only) builds Documents from the fixtures with script execution disabled.
- **Adversarial review fixes (15-agent verify workflow, before commit; 3 must-fix).** (1, must) The DOM fallback treated a generic marketing `og:description` as a listing, so opening on a Rightmove/Zoopla home/search page returned a hollow `ok:true` — and a stray `"pricing"` on a Zoopla search page could yield a WRONG price via the embedded path. Both extractors now require a listing-DETAIL URL id (`/properties/<n>` or `/details/<n>`) plus a real content field; the Zoopla embedded path is gated on a `/details/` URL. Non-listing pages now return a typed failure. (2, must) The fallback fabricated an address from the raw `og:title` (e.g. `Property for sale in Swansea | Zoopla`); `parseZooplaLdName` now returns null on no-match and Rightmove strips the `| Rightmove` brand suffix + pipe leak, so address is only ever a real one. (3, must) `refreshRemoteConfig` could never re-fetch R2 once the cache was warm (stale-forever) — added a `forceRemote` bypass the panel refresh uses; it updates the cache on success, leaves it intact on failure. (4) `decodeZooplaFlight` used a non-greedy regex that truncated a chunk at the first `"])"` inside a string value (silently dropping the whole model); it now bracket-scans the push argument respecting string escapes. (5) `newBuild` is `found(false)` only when a signal was actually present (else `missing`) — no more asserting "definitely not a new build" from absence. (6) Test honesty: the E&W-message check now asserts the literal string (not a self-referential constant), and the config-disabled test asserts the typed reason so a swallowed throw would fail.

Web app unchanged.

## 2026-09-02 — Sprint E2.1: deal-specific verdict headlines

- **Problem.** Three of the four live analysers returned the identical chip headline ("It works, but only just — the margins are thin") because the headline was tier-generic. The useful sentence (the binding constraint with real numbers) was buried in the card.
- **Fix.** `DealScore.headline` is now built from THIS deal's binding constraint, carrying its deciding figure. Failing deals key off the binding component (`scoreCopy.headlineByKey`): ROI → "Just 5.0% back on the cash you'd tie up, short of the 8.0% that makes the risk worth it"; money-left-in → "£26,140 would stay stuck after refinancing — pay £96,250 or less to get it all back out"; plus icr / cashflow / profit / evidence / roomSize, each naming its own number.
